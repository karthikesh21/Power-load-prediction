# Power Load Prediction 

[![Python 3.10+](https://img.shields.io/badge/python-3.10%2B-blue.svg)](https://www.python.org/downloads/)
[![scikit-learn](https://img.shields.io/badge/scikit--learn-1.3%2B-orange.svg)](https://scikit-learn.org/)

An end-to-end Machine Learning classification system designed to predict the **Load Type** (`Light_Load`, `Medium_Load`, `Maximum_Load`) of an industrial power network from chronological electricity consumption and electrical sensor measurements.

---

## 1. Project Overview & Business Motivation

Modern electrical grids, smart meter infrastructures, and industrial power management systems rely heavily on accurate automated categorization of facility electrical demand:

- **`Light_Load`**: Off-peak, idle, nighttime, or weekend periods characterized by minimal active power draw and dominant capacitive reactance.
- **`Medium_Load`**: Standard operational load during normal daytime factory shifts and operational transitions.
- **`Maximum_Load`**: Peak industrial capacity where heavy inductive machinery, pumps, and motors operate concurrently.

### Primary Engineering Objectives
1. **Demand-Response Optimization**: Enable grid operators to adjust automated power dispatch and avoid localized transformer overloads.
2. **Leakage-Free Temporal Modeling**: Strictly enforce chronological data splits (training on historical months, holding out the final calendar month for out-of-time test evaluation).
3. **Robust Data Hygiene**: Uncover and rectify real-world sensor defects, duplicate timestamps, and corrupted pre-engineered columns (`NSM`).
4. **Production-Ready Inference**: Deliver a serialised pipeline and standalone prediction interface (`src/predict.py`) for live telemetry ingestion.

## 2. Problem Statement & Dataset Architecture

The project classifies multi-class power demand using continuous telemetry gathered at **15-minute intervals** across the entire 2018 calendar year:

| Column Name | Type | Physical Meaning & Units |
| :--- | :--- | :--- |
| `Date_Time` | String / Datetime | Timestamp of observation (`DD-MM-YYYY HH:MM`) |
| `Usage_kWh` | Continuous Float | Industry active energy consumption ($kWh$) |
| `Lagging_Current_Reactive.Power_kVarh` | Continuous Float | Lagging reactive power drawn by inductive loads ($kVarh$) |
| `Leading_Current_Reactive_Power_kVarh` | Continuous Float | Leading reactive power generated by capacitive effects ($kVarh$) |
| `CO2(tCO2)` | Continuous Float | Greenhouse gas emissions equivalent ($tCO_2$) |
| `Lagging_Current_Power_Factor` | Continuous Float | Inductive power factor ($0\\%$ to $100\\%$) |
| `Leading_Current_Power_Factor` | Continuous Float | Capacitive power factor ($0\\%$ to $100\\%$) |
| `NSM` | Continuous Float | Number of seconds elapsed from midnight ($0$ to $86,400s$) |
| **`Load_Type`** (Target) | Categorical String | **`Light_Load`**, **`Medium_Load`**, **`Maximum_Load`** |

### Key Data Quality Findings (Empirical Audit)
1. **Redundant Duplicate Timestamp**: The raw file contains 35,041 observations. Exactly 35,040 intervals represent 365 days ($365 \\times 24 \\times 4 = 35,040$). Timestamp `31-12-2018 20:00` appeared twice; the duplicate record contained a missing `Usage_kWh` and an impossible power factor of $217.27\\%$. It was safely dropped.
2. **Missing Values**: Present across all measurement columns (~1.0% to 4.5%), with `Usage_kWh` missing 1,559 values. Handled via median imputation strictly inside training pipelines.
3. **Corrupted `NSM` Column**: Exactly **9.87% (3,414 rows)** of raw `NSM` entries exhibited corruption and time drift (exceeding 86,400s and reaching 248,821s). The project replaces this with verified `seconds_from_midnight` calculated directly from parsed timestamps.
4. **Class Imbalance**:
   - `Light_Load`: **18,073 records (51.58%)**
   - `Medium_Load`: **9,696 records (27.67%)**
   - `Maximum_Load`: **7,272 records (20.75%)**
   - *Implication*: Macro F1 is the required metric to evaluate minority class performance equitably.

## 7. Chronological Validation & Leakage Prevention Strategy

The problem statement explicitly requires using the **last calendar month** as the final test set. 

```
2018-01-01                                     2018-10-31 2018-11-30 2018-12-31
[================= Training Sub-Split ==================][== Val ==][== Test ==]
                   Jan 1 to Oct 31, 2018                   Nov 2018    Dec 2018
                   (29,184 observations)                  (2,880 obs) (2,976 obs)
                                                                           ▲
                                                           Untouched Final Evaluation
```

1. **Dynamic Test Set Partition**: The final complete calendar month (dynamically detected from dataset timestamps as **December 2018**, 2,976 observations) was isolated at the very start and never touched during EDA, preprocessing fit, cross-validation, or model selection.
2. **Dynamic Validation Strategy**: To evaluate models without data leakage during iterative tuning, the calendar month immediately preceding the test set (dynamically detected as **November 2018**, 2,880 observations) served as our out-of-time validation holdout.
3. **Pipeline Encapsulation**: Imputation medians and scaling parameters are computed strictly on training data inside `sklearn.pipeline.Pipeline`.

### Analysis of Predictions & Misclassification Drivers
1. **Light Load High Reliability**: The model isolates off-peak and standby periods with high precision (**98.10% precision, 91.97% recall, 0.9494 F1 score**).
2. **Medium vs. Maximum Overlap (Root Operational Bottleneck)**:
   - Out of 704 actual `Medium_Load` events, 361 were correctly identified (51.28% recall), while 324 (46.02%) were predicted as Maximum Load.
   - Out of 528 actual `Maximum_Load` events, 245 were correctly identified (46.40% recall), while 271 (51.33%) were predicted as Medium Load.
   - In industrial facilities, Medium and Maximum loads share identical daytime factory shifts (08:00 to 20:00 on weekdays), similar inductive reactive powers, and overlapping kilowatt ranges. In December, seasonal shifts in manufacturing throughput cause active power readings to oscillate across the decision boundary.
3. **Mathematical Invariant Verification**: All 7 mathematical invariants connecting the confusion matrix directly to the classification report (row sums = support, diag/row sum = recall, diag/col sum = precision, accuracy = sum of diags/total, macro F1 = mean of class F1s, weighted F1 = support-weighted mean) are verified via automated assertions.

## 9. Feature Importance & Interpretability (Permutation Importance)

- **`seconds_from_midnight`**: Dominant predictor (Mean Macro F1 drop: ~0.1837). Industrial shift schedules provide the strongest prior information distinguishing active shifts from nighttime standby.
- **`Usage_kWh`**: Primary continuous electrical driver (~0.0270 Macro F1 drop). Direct active energy consumption demarcates baseline from heavy manufacturing operations.
- **`dayofweek`**: Third key predictor (~0.0260 Macro F1 drop). Captures weekday vs. weekend production rhythms.
- **`Lagging_Current_Reactive.Power_kVarh`**: Essential for identifying inductive machinery (compressors, large motors).
- **`CO2(tCO2)`**: Strongly correlated with active thermal generation and industrial machinery dispatch.

## 10. Limitations & Future Roadmap

1. **Single-Year Time Horizon**: Multi-year datasets would allow capturing year-over-year manufacturing growth and long-term climate cycles.
2. **Telemetry Filtering**: Telemetry pre-processors should clip physically impossible power factors ($>100\%$) before model ingestion.
3. **Sequential Autocorrelation**: Incorporating $t-1$ and $t-4$ lag features would provide localized momentum information if streaming history is available.
